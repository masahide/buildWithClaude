# 全体構成

```
iPhoneアプリ ──特徴量+写真──> 薄いサーバー ──セッション開始──> Managed Agents
     ^                            |    ^                         (コーチ)
     └──────プッシュ通知────────────┘    └──────Webhook──────────────┘
                                                    ^
                              夜のスケジュール実行 ─┘（メモリストアを更新）
```

| コンポーネント | 役割 |
| --- | --- |
| iPhone アプリ | 音と写真を集め、音響特徴量を端末内で計算する。「あなたの正解」を表示する |
| 薄いサーバー | API キーを持つ中継役。セッション開始、Webhook 受信、プッシュ通知 |
| Managed Agents | コーチ本体。1杯ごとの診断と予測、次の杯での検証、夜の振り返り |

## iPhone アプリ（音と写真を集める）

- バックグラウンドで録音する。練習開始時の数秒で背景音量を測り、基準にする
- スチーム区間の検出: 基準に対する帯域エネルギーの比で鳴り始めと鳴り終わりを判定する。短い途切れ（空ぶかしなど）は1区間に統合し、最低継続時間に届かないもの（グラインダー、ケトルなど）は弾く。自動検出が不安定な環境のために、手動の「杯を区切る」ボタンも残す
- 音響特徴量を端末内で計算する。端末差・置き場所の差・窓を開けた環境の差に耐えるため、**すべて相対値**にする

  | 特徴量 | 意味 | 主に効く工程 |
  | --- | --- | --- |
  | エア入れ相の時間比率 | 「紙を裂く音」が続く時間の割合 | エア入れ |
  | 移行タイミング | エア入れ相から撹拌相（渦に入って静かになる）へ移るタイミング | エア入れ→撹拌 |
  | 撹拌相の安定度 | 撹拌相の音の揺らぎの小ささ | 撹拌 |
  | 撹拌相の低域比率 | こもった轟音の割合。ノズルが深すぎる疑い | 撹拌 |
  | 大きな泡の破裂音の回数 | 「ゴボゴボ」の回数。渦ができていない疑い | 撹拌 |
  | 包絡 | 3帯域の相対エネルギーを0.1秒ごとに記録した数列。相の形をコーチが直接読む（[decisions.md D6](decisions.md#d6-音響特徴量に包絡を加える)） | 全体 |

- 区間が終わると通知 → 注ぎ終わったらカップとピッチャーを並べて写真1枚（[decisions.md D5](decisions.md#d5-完成写真にピッチャーの残りを入れる)） → 任意で自己評価
- 特徴量・包絡・写真・自己評価をサーバーへ送信し、診断結果はプッシュ通知で受け取る
- `/rules.md` の内容を「あなたの正解」として一覧表示する
- 生の音声は送信しない

## 薄いサーバー（API キーを持つ中継役）

- `POST /cups`: 写真をアップロードし、Managed Agents のセッションを開始して特徴量・包絡・写真・自己評価を渡す。Outcomes のルーブリックを定義する
- Webhook 受信: セッション終了（`session.status_idled` など）で結果を取り出し、APNs でプッシュ通知する
- 朝の通知: 夜の振り返りが書いた「今日のテーマ」を決まった時刻に通知する
- API キーは環境変数で管理し、公開リポジトリに入れない
- インフラは本人の得意なものでよい。処理は上記だけに留める

## Managed Agents（コーチ本体）

### エージェント「コーチ」

1体だけ置く。役割は「症状から原因の工程をちょうど1つ特定し、次の1杯で直す点1つと、次の杯で観測できる予測1つを返す。前の杯に予測があれば、その当否を先に判定する」（[decisions.md D7](decisions.md#d7-診断を仮説と予測の形にし次の杯で検証する)）。

原因は、エア入れ（音）→ 撹拌（音とピッチャーの残り）→ 注ぎ（完成形からの推定）の順に割り当てる（[decisions.md D4](decisions.md#d4-工程の区分をエア入れ撹拌注ぎにする)）。注ぎの動作は動画を使わず完成形から推定する（例: 縦に伸びた → 最後の抜きが長い）。

写真の所見は毎杯、固定の軸で数値化して記録する。杯をまたいだ比較と、夜の振り返りの根拠にする。

| 対象 | 軸 | スケール |
| --- | --- | --- |
| カップ | 輪郭の鮮明さ、白茶のコントラスト、位置と形 | 各 0〜2 |
| ピッチャーの残り | 泡の大きさ、泡の固さ、艶 | 各 0〜2 |

### メモリストア（ユーザーごとに1つ）

各セッションは白紙で始まるため、杯をまたいだ記憶はメモリストアに持たせる。期間中に作った内容を事前に投入する。

| パス | 中身 | 書く人 |
| --- | --- | --- |
| `/profile.md` | 固定条件（マシン、ノズルの穴数、ピッチャー容量、ミルク銘柄と量、豆、カップ、目標技法スローハート） | 本人（事前投入） |
| `/rubric.md` | 工程ごとの症状→原因→指示→期待される変化の表と、ノズル位置・深さ・渦・折り込みの基本。競技会の審査基準を出典に、本人の失敗ログから期間中に新規作成し、育てる | 本人＋コーチ |
| `/cups/YYYY-MM-DD-N.md` | 1杯ごとの特徴量、写真所見のスコア、自己評価、診断、予測、前の杯の予測の当否 | コーチ |
| `/tendencies.md` | 杯をまたいだ癖のまとめ | 夜の振り返り |
| `/rules.md` | 効いた直し方の一覧。本人の機材とミルクでの正解（「あなたの正解」） | 夜の振り返り |
| `/today.md` | 今日のテーマ1つ | 夜の振り返り |

### 1杯ごとの診断セッション＋Outcomes

採点役が、次のルーブリックを満たさない回答を差し戻す。

- 原因の工程はちょうど1つ（エア入れ／撹拌／注ぎ）
- 直す点はちょうど1つ。複数の指摘を含まない
- 直す点は耳・手・時間で実行できる。cm や温度の測定を要求しない（[decisions.md D8](decisions.md#d8-指示は耳手時間で実行できる言葉に限る)）
- 次の杯で観測できる予測がちょうど1つ付いている
- 根拠が、今回の音響特徴量か写真の所見のどちらかにある
- 前の杯に予測があれば、その当否を述べている
- `/tendencies.md` と過去の杯の記録に矛盾しない。矛盾する場合はその理由を述べる

診断の待ち時間によっては、1杯ごとの診断を Messages API に切り替える可能性がある（[plan.md](plan.md#今日11-03確かめること) の確認項目2）。

### 夜の振り返り（スケジュール実行）

毎晩、メモリストアを付けたセッションを cron で起動する。

1. その日の `/cups/` を読む
2. 予測の当否を集計し、効いた直し方を `/rules.md` に加える。効かなかった仮説は `/rubric.md` の見直し候補として記す
3. 杯をまたいだ癖を見つけて `/tendencies.md` を更新する（例: エア入れ相が長い杯ほど輪郭が滲む）。癖は2杯以上の数値を引いて述べる（Outcomes で強制）
4. 明日のテーマ1つを `/today.md` に書く

Dreaming（研究プレビュー、申請制）の承認が下りたら、この自前の振り返りを Dreaming に置き換える。承認が来なくても体験は成立する。

## 運用上の注意

Managed Agents のセッション履歴は削除するまで残る。メモリストアとアップロードしたファイルはセッションを消しても残るため、提出後に不要なら個別に削除する。
