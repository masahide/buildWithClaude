# 全体構成

```
iPhone アプリ（台所に置く）            自宅の Mac（サーバー）                     Claude Managed Agents
 マイク → 0.1秒ごとの帯域の音量                                                    （コーチ）
   → 判定・特徴量・包絡 ─────┐
 練習の音（全部、48kHz WAV）──┼──POST /cups──> 杯・音・写真を保存
 ピッチャーの残りの写真 1枚 ──┘                  今の判定の版で測り直す
                                                 音の絵を描く ──数値・音の絵・写真──> 1杯の診断＋Outcomes
     ^                                           │                                   （メモリストアを読む）
     └──GET /cups/{id}（3秒ごと）── 診断 <────────┘
     ┌──GET /coach・/params・/params/proposal ── メモリストア・判定の版
     └──POST /teach・/params/proposal/{accept|reject}
                                       POST /review（手で起動）──包絡・音の絵──> 夜の振り返り＋Outcomes
                                                                                  （メモリストアに書く・閾値を提案）
```

音声はサーバーの Mac の中にだけ置く。Claude に渡すのは、音から作った数値・音の絵（画像）・ピッチャーの写真だけである（[decisions.md D21](decisions.md#d21-音声をサーバーに送り何度でも測り直せるようにする約束を家の外に出さないに改める)）。

| コンポーネント | 役割 |
| --- | --- |
| iPhone アプリ（[ios/](../../ios/)、SwiftUI） | 録音し、端末内で判定と特徴量を計算する。杯ごとに特徴量・包絡・写真・音をサーバーへ送る。診断、今日のテーマ、あなたの正解、コーチが学んだことを表示する。コーチに教え、判定の調整の提案を承認する |
| サーバー（[server/](../../server/)、FastAPI） | 自宅の Mac で動き、API キーを持つ。杯と音を保存し、今の判定の版で測り直し、音の絵を描き、コーチを呼ぶ。判定の閾値を版つきで持つ |
| コーチ（Managed Agents） | 1杯ごとの診断と予測、前の杯の予測の当否。夜の振り返りで記憶を育て、根拠があれば閾値の変更を提案する |
| メモリストア | 杯をまたいだ記憶。この人のやり方、音の読み方、あなたの正解、癖、今日のテーマ、判定の版の履歴 |

## iPhone アプリ

### 録音と判定

- 「練習を開始」で録音を始める。ロックしても録音は続く。最初に `GET /params` で判定の閾値の今の版を取りに行く。取れなければアプリの既定値で判定し、版は記録しない
- 最初の3秒で背景音を測る（中央値）。特徴量はすべて背景音や区間内の比にした相対値である
- マイクの音（ふつう 48 kHz）を 0.1 秒ごとの帯域の音量に変える。帯域は低 50–400 Hz、中 400–2000 Hz、高 2000–8000 Hz、最高 4000–8000 Hz の4つ。最高の帯域は撹拌中のチリチリを見るためのもので、判定には使わない（[decisions.md D19](decisions.md#d19-コーチに加工前の音の形も渡す音の絵と包絡)）
- スチームの終わりを逐次判定し、終わったらローカル通知「スチーム終了」を出す
- 杯の区切りは手動である。本人が「この杯を区切って撮る」を押すと、その時点までの帯域の音量から特徴量を計算する。自動の区切りと、一定時間で練習を自動で終える仕組みはない（[decisions.md D11](decisions.md#d11-最初の一周は手動区切りで回し自動区切りと包絡を後回しにする)）

判定の計算は [FeatureExtractor.swift](../../ios/LatteCoach/Audio/FeatureExtractor.swift) の1か所だけに置く。サーバーの測り直しも、同じ Swift をコンパイルして使う（[decisions.md D16](decisions.md#d16-音を絵にして-claude-に見せ判定は端末の数値のままにする)）。

- スチーム区間: 始まりは、1秒平均の音量が背景より `onset_db` を超えた状態が `onset_sustain_sec` 続いたところ。続きは、高域と低域の音量の差の1秒平均が `tilt_stay_db` を `end_quiet_sec` 下回るまで（判定の版 v2。[decisions.md D22](decisions.md#d22-スチームの終わりを全体の音量ではなく高域と低域の差で決める判定の版-v2)）
- 始めのキュルルル: 区間の先頭で高域の割合が高い間。泡入れに含めない
- 泡入れ（ジュルジュル）: 音量の揺れが大きい区間。最初の泡入れと追加の泡入れを別に数える。短い揺れはゴボゴボとして泡入れに数えない（[decisions.md D15](decisions.md#d15-スチームの区間と相の判定を実際の録音に合わせて作り直す)、[D17](decisions.md#d17-泡入れを1回と決めつけず追加の泡入れを別に数える)）
- 渦への境: 最後の泡入れの終わり。撹拌の値は、止める間際のキュルキュルを除いて測る

| 特徴量 | 意味 | 主に効く工程 |
| --- | --- | --- |
| `steam_duration_sec` | スチーム区間の長さ（秒） | 全体 |
| `start_squeal_sec` | 始めのキュルルルの長さ（秒） | エア入れ |
| `air_phase_ratio` | 区間のうち泡入れが占める割合。追加の泡入れを含み、キュルルルは含まない | エア入れ |
| `first_air_sec` | 最初の泡入れの長さ（秒） | エア入れ |
| `re_air_count`・`re_air_sec` | 一度渦に入ってから追加で泡入れした回数と合計の長さ | エア入れ |
| `transition_at` | 最後の泡入れから渦へ移った位置（区間の先頭からの割合） | エア入れ→撹拌 |
| `stir_stability` | 撹拌相の音の滑らかさ（1 に近いほど滑らか） | 撹拌 |
| `stir_low_band_ratio` | 撹拌相の低域の割合。高いとノズルが深すぎる疑い | 撹拌 |
| `burst_count` | 撹拌相で中域が急に大きくなった回数（ゴボゴボ） | 撹拌 |
| `level_over_background_db` | 区間の音量の背景音比。置き場所の目安で、診断の根拠にしない | - |

撹拌中のチリチリは数えていない。

### 杯を送る

区切ると写真の画面が開き、ピッチャーの残りを1枚撮る（カップを並べるのは任意。[decisions.md D5](decisions.md#d5-完成写真にピッチャーの残りを入れる)、[D10](decisions.md#d10-対象をミルクスチームに特化し工程をエア入れ撹拌の2つにする)）。自己評価は任意で、「良かった／泡が多すぎた／泡が少なすぎた／泡が粗かった」から選ぶ。写真を撮ると送れる。

`POST /cups` で次を送る。

- `meta`（JSON）: 特徴量、包絡（4帯域の背景音比を 0.1 秒ごと、有効数字3桁。[decisions.md D14](decisions.md#d14-包絡を閾値の調整のために先に送る)）、判定の境の位置 `marks`（始まり、キュルルル終わり、渦へ、止めた）、判定の版 `params_version`、自己評価、背景音、練習 ID と区間番号、音の先頭の位置
- `photo`: ピッチャーの残り（JPEG）
- `audio`: 前回の区切りからこの区切りまでの音を全部（48 kHz・16 bit の WAV）。送れたら端末から消す

練習を終了すると、最後の区間の音を `POST /practices/{練習ID}/audio/{区間番号}` で送る。こうして練習の音が開始から終了まで全部、自宅の Mac に残る（[decisions.md D21](decisions.md#d21-音声をサーバーに送り何度でも測り直せるようにする約束を家の外に出さないに改める)）。

### 結果を受け取る

- 診断はアプリが `GET /cups/{id}` で3秒ごとに取りに行く（最大10分）。届いたらローカル通知を出す。リモートのプッシュ通知は使わない（[decisions.md D12](decisions.md#d12-無料の-apple-id-で開発しリモートのプッシュ通知を使わない)）
- 起動時に、送信中で止まった杯は送り直せるようにし、診断中の杯は取りに行くのを再開する
- 杯の一覧に、前の杯の予測の当否、原因の工程、次の1杯で直す点、起きるはずの変化を出す

### コーチと一緒に育つ

アプリの「コーチと一緒に育つ」の欄に、次を出す（[decisions.md D18](decisions.md#d18-ai-もユーザーも初心者から始まり一緒に育つコーチにする)）。開いたときと引っ張って更新したときに取りに行く。

- `GET /coach`: 今日のテーマ、あなたの正解、コーチが学んだこと、杯をまたいだ癖
- コーチに教える: 本人が書いた一文を `POST /teach` で送る（例: 「27〜32秒は追加の泡入れだった」）
- `GET /params/proposal`: コーチから判定の調整の提案があれば、変更・理由・根拠・各値の意味を出す。本人が「適用する」か「見送る」を押す（`POST /params/proposal/accept`・`/reject`）
- 今の判定の版。次に練習を開始したときから使われる

朝の通知はない。今日のテーマは、アプリを開いたときに出る。アプリで音の絵を見る画面もない。

## サーバー

実装は [server/](../../server/)（FastAPI）。自宅の Mac で動かす。API キーは環境変数で持ち、リポジトリに入れない。

### エンドポイント

| エンドポイント | 中身 |
| --- | --- |
| `POST /cups` | 杯を受け取る（`meta`・`photo`・`audio`）。保存して 202 で `cup_id` を返し、裏で診断を始める |
| `GET /cups/{id}` | 診断の状態（`diagnosing`／`done`／`failed`）、診断、エラー、かかった秒 |
| `GET /cups/{id}/sound.png` | 杯の音の絵。README・デモ・本人の確認用 |
| `POST /practices/{練習ID}/audio/{区間番号}` | 杯につかない練習の音（終了時の最後の区間） |
| `GET /coach` | メモリストアの今日のテーマ、あなたの正解、この人の音の読み方、杯をまたいだ癖 |
| `POST /teach` | 本人が教えたことを、記憶の `/reading.md` に日付つきで書き足す |
| `GET /params` | 判定の閾値の今の版と値 |
| `GET /params/proposal` | 承認待ちの提案（なければ null）、今の版、各値の意味 |
| `POST /params/proposal/{accept\|reject}` | 提案を適用するか見送る。結果を記憶の `/params.md` に書き足す |
| `POST /review?day=YYYY-MM-DD` | 夜の振り返りを裏で回す。結果は `server/data/reviews/` に残る |
| `GET /health` | 動いているかの確認 |

Webhook の受信はない。サーバーから端末へ通知を送る仕組みもない。

### 1杯の処理

`POST /cups` を受けたら、裏で次を行う。

1. 直前に診断が済んだ杯を探す（二重に届いた杯は除く）。その特徴量・自己評価・診断と、音の絵を前の杯として渡す
2. 音があれば、今の判定の版で測り直す。アプリが出した値は `features_app`・`marks_app` に残し、診断には測り直した値と版を使う。アプリが古くても、診断には今の判定が使われる（[decisions.md D22](decisions.md#d22-スチームの終わりを全体の音量ではなく高域と低域の差で決める判定の版-v2)）
3. 音の絵（`sound.png`）を描く（[server/sound_picture.py](../../server/sound_picture.py)、[sound-picture.md](sound-picture.md)）。上から、音から描いたスペクトログラム（音があるとき。背景音比、0.1 秒刻み）、包絡から描いた帯域ごとの音量、音量の揺れ。縦線は判定の境。描く範囲は始まりの5秒前から止めた5秒後まで。音の絵は音声ではなく、0.1 秒より細かくしないので音声に戻せない
4. コーチに診断させ、結果を `status.json` に書く

サーバーが診断の途中で止まった杯は、起動時に診断し直す。

診断の方式は環境変数 `COACH_BACKEND` で切り替える。

| 値 | 方式 |
| --- | --- |
| `managed`（既定） | Managed Agents のセッション＋Outcomes。メモリストアを読む（[decisions.md D13](decisions.md#d13-1杯ごとの診断を-managed-agentsoutcomes-で回す)） |
| `messages` | Messages API を1回。速いが採点役がなく、メモリストアも読まない |
| `fake` | API を呼ばず固定の診断を返す。通しの確認用 |

`COACH_SOUND_PICTURE=0` で音の絵を渡さないようにできる。

### データの置き場所

すべて `server/data/`（git 管理外）に置く。

| パス | 中身 |
| --- | --- |
| `cups/<杯ID>/` | `meta.json`（送られた中身と測り直しの結果）、`status.json`（状態と診断）、`photo.jpg`、`audio.wav`、`sound.png` |
| `practices/<練習ID>/<区間番号>.wav` | 練習の音の通し。杯につく区間は `cups/` の音と同じファイル（ハードリンク） |
| `params/` | 判定の版ごとの閾値、今の版、承認待ちの提案 |
| `reviews/<日付>.json` | 夜の振り返りの結果 |
| `managed_ids.json`・`memory_ids.json` | Managed Agents のエージェント・環境・メモリストアの ID |

音声はここにだけ置き、GitHub にも Anthropic（Claude）にも送らない。サーバーを自宅の外（クラウド）に移すときは、この約束を見直す（[decisions.md D21](decisions.md#d21-音声をサーバーに送り何度でも測り直せるようにする約束を家の外に出さないに改める)）。

## コーチ（Managed Agents）

### エージェント

エージェント「スチームコーチ」を1体だけ置き、1杯の診断と夜の振り返りの両方に使う。初回の診断で、エージェント・環境・メモリストアを作る。プロンプトを変えると、保存してあるエージェントを新しい版に更新する。環境の外へのネットワークは制限し、Web の取得と検索は切ってある。

役割は「症状から原因の工程をちょうど1つ特定し、次の1杯で直す点1つと、次の杯で観測できる予測1つを返す。前の杯に予測があれば、その当否を先に判定する」（[decisions.md D7](decisions.md#d7-診断を仮説と予測の形にし次の杯で検証する)）。原因はエア入れ（音）か撹拌（音とピッチャーの残り）に割り当てる。注ぎやカップの模様は診断・採点しない。カップが写っていても、ピッチャーの所見の裏付けにだけ使う（[decisions.md D10](decisions.md#d10-対象をミルクスチームに特化し工程をエア入れ撹拌の2つにする)）。音で分からないもの（渦の回転方向、縦横の撹拌のバランス、ノズルの正確な位置と深さ）は、観測したかのように書かせない（[decisions.md D9](decisions.md#d9-音で分からないものを明文化する)）。

### 1杯ごとの診断＋Outcomes

セッションにメモリストアを読むだけで付け、`/profile.md`・`/reading.md`・`/rules.md`・`/today.md` を読んでから診断させる。

渡すもの:

- 今回の杯の特徴量（判定の版つき）と自己評価
- 前の杯の記録（特徴量、自己評価、診断）
- 音の絵: 前の杯と今回の杯。数値を正とし、絵は数値に出ない形を読む補助。絵を根拠にするときは何秒あたりの何を見たかを書かせる（[decisions.md D19](decisions.md#d19-コーチに加工前の音の形も渡す音の絵と包絡)）
- ピッチャーの残りの写真

返すもの:

| 項目 | 中身 |
| --- | --- |
| `process` | 原因の工程（エア入れ／撹拌） |
| `fix` | 次の1杯で直す点1つ。耳・手・時間で実行できる言葉 |
| `prediction` | 次の杯で観測できるはずの変化1つ |
| `evidence` | 根拠（今回の特徴量か写真の所見） |
| `previous_verdict` | 前の杯の予測の当否。前の杯がなければ null |
| `photo_scores` | ピッチャーの残りの泡の大きさ・泡の固さ・艶（各 0〜2） |
| `sound_observation` | 音の絵から読んだ、数値に出ていない形 |
| `judgment_doubt` | アプリの判定の線が絵と食い違って見えた点。判定の作り直しに使う |

Outcomes の採点役が、次のルーブリックを満たさない回答を差し戻す（最大3回）。

- 原因の工程がエア入れ・撹拌のちょうど1つ
- 直す点はちょうど1つで、複数の指摘を含まない
- 直す点は耳・手・時間で実行できる。cm・温度・角度の測定を要求しない（[decisions.md D8](decisions.md#d8-指示は耳手時間で実行できる言葉に限る)）
- 次の杯で観測できる予測がちょうど1つ付いている
- 根拠が、今回の音響特徴量か写真の所見にある
- 前の杯の診断があれば、その予測の当否を述べている
- 注ぎやカップの模様を診断・採点していない
- 写真の所見が各 0〜2 の数値で記されている
- 末尾に指定の JSON がある

診断の JSON は返答から取り出す。返答になければ、コーチが作業用の環境に書いたファイルから読む。送ってから診断が届くまで、1〜3分ほどかかる。

### 夜の振り返り

自動では起動しない。本人が `POST /review?day=YYYY-MM-DD`（または `uv run python review.py YYYY-MM-DD`）で手で起動する。1回 30 分ほどかかる。

1. その日の杯（二重に届いた杯は除く）の特徴量・自己評価・診断をまとめて渡す
2. 各杯の包絡（JSON）と音の絵（PNG）をファイルとしてアップロードし、作業用の環境の `/workspace/cups/` に置く。コーチは Python で包絡を解析し、杯どうしの形を比べてよい。音声は置かない
3. メモリストアを読み書きできる形で付け、ルーブリックに沿って記憶に書き足させる
   - その日の杯の記録を `/cups/<日付>.md` に
   - 予測が当たった直し方を `/rules.md`（あなたの正解）に、「状況 → 直し方 → 起きた変化」の形で
   - 分かった音の読み方と、外れた予測の理由を `/reading.md` に。何秒あたりの何を見たかを添える
   - 杯をまたいだ癖を `/tendencies.md` に。2杯以上の数値を引いて述べる
   - 明日のテーマちょうど1つを `/today.md` に。耳・手・時間で実行できる言葉で
   - 既存の内容は消さない。「本人から教わったこと」と食い違う読みをしない
4. 最後に、判定の閾値を変えたほうがよいかを考えさせる。根拠があるときだけ提案させ、サーバーが提案として保存する（次の節）

Outcomes の採点役が、このルーブリックを満たさない振り返りを差し戻す（最大3回）。

Dreaming（研究プレビュー、申請制）は 11-03 に申請したが、使っていない。夜の振り返りは自前の Managed Agents のセッションで回している。

## メモリストア

ユーザーごとに1つ（今は本人の1つだけ）。各セッションは白紙で始まるので、杯をまたいだ記憶はここに持たせる。初回に、11-03〜11-07 に本人と分かったことを最初の中身として入れる（[server/memory.py](../../server/memory.py)）。1杯ごとの診断は読むだけ、夜の振り返りが書く（[decisions.md D18](decisions.md#d18-ai-もユーザーも初心者から始まり一緒に育つコーチにする)）。

| パス | 中身 | 書く人 |
| --- | --- | --- |

## 判定の版

判定の閾値はサーバーが版つきで持つ（[server/params.py](../../server/params.py)、[decisions.md D20](decisions.md#d20-判定の閾値はコーチが提案し本人が承認して変える)）。コーチは黙って閾値を書き換えない。物差しが黙って変わると、予測の検証ができなくなるからである。

- 閾値は10個（スチームの始まりと終わり、最低の長さ、キュルルル、泡入れ、キュルキュル、ゴボゴボ）。それぞれ既定値と、許す範囲を持つ。既定値はアプリの既定値と同じ
- v1 は 11-05 のボイスメモと本人の耳で合わせた最初の値。v2 は、スチームの終わりを高域と低域の差で決めるように判定の方法を変えた版（[decisions.md D22](decisions.md#d22-スチームの終わりを全体の音量ではなく高域と低域の差で決める判定の版-v2)）。判定の方法の変更は、本人と開発で決めて版を上げる
- アプリは練習の開始時に今の版を取りに行き、杯ごとに版を記録する。音のある杯は、サーバーが今の版で測り直してから診断する
- 版が違う杯どうしは、数値を直接比べない。コーチにも版を伝え、`/params.md` の履歴を読ませる

提案と承認の流れ:

1. 夜の振り返りで、コーチが包絡の解析や本人に教わったことを根拠に、変えたほうがよいと言えるときだけ提案する
2. サーバーが提案を検査する。知らない名前は捨て、範囲の外は範囲に収める。今と同じ値は除く
3. サーバーが、音のある直近の杯（最大10杯）を今の値と提案の値で測り直し、結果を提案に添える（`GET /params/proposal` の `replay`・`replay_summary`）。測り直しは [server/rejudge.py](../../server/rejudge.py) が、アプリと同じ Swift の判定をこの Mac でコンパイルして行う
4. 本人がアプリで変更・理由・根拠を見て、適用するか見送るかを決める。適用すると版が上がる。どちらでも `/params.md` に残る

音の絵の描き方をコーチが自分で変える仕組みは、まだない。

## 運用上の注意

Managed Agents のセッション履歴は削除するまで残る。メモリストアと、夜の振り返りでアップロードした包絡と音の絵のファイルは、セッションを消しても残る。提出後に不要なら個別に削除する。サーバーの `server/data/` の音声と写真は、本人がいつでも消せる。
