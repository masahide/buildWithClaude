## 今日（11-03）確かめること

1. **Dreaming の利用申請を出す。** 承認までの時間が読めないため最優先
2. **診断セッションの待ち時間を測る。** コンソールでエージェントを1つ作り、テスト杯の写真でセッションを1回回す。Outcomes が「1点だけ」に絞るかも同時に確認する
   - 数十秒〜1分程度なら、1杯ごとの診断も Managed Agents で回す
   - 数分かかるなら、1杯ごとの診断は Messages API にメモリの中身を渡して呼び、Managed Agents は夜の振り返りと記録の蓄積に絞る
3. **カウンター置きで録音する。** ボイスメモで2〜3杯を通し録音する。窓はいつも通りの状態で、杯の自動区切りとエア入れ相の検出ができるか確認する。あわせて、ノズルを深く入れすぎたときのこもった轟音と、正常な撹拌相の静けさが耳で区別できる形で録れているかを聞く
4. **ピッチャーの残りを撮る。** 今日の杯から、注ぎ終わりにピッチャーの残りを1枚撮る。残りの泡の大きさ・固さ・艶が写真で読めるか確認する（[decisions.md D5](decisions.md#d5-完成写真にピッチャーの残りを入れる)、[D10](decisions.md#d10-対象をミルクスチームに特化し工程をエア入れ撹拌の2つにする)）

結果は [docs/log/](../log/) に書き、判断が出たら [decisions.md](decisions.md#未決) を更新する。

## 時間が足りないときに削る順

上から順に削る。下に行くほど製品の芯に近い。

1. 「あなたの正解」の一覧画面（`/rules.md` は残し、表示だけ落とす）
2. コーチに音の絵を渡すこと（特徴量の数値と写真だけで診断する。杯ごとの絵は描いて README とデモに使う。[sound-picture.md](sound-picture.md)）
3. 包絡の送信（スカラー値だけにする）
4. 練習の自動終了（「終了」ボタンだけにする）
5. 結果の通知（アプリを開いたときに結果を取りに行く形にする）。リモートのプッシュ通知は D12 で使わないことにした
6. 杯の自動区切り（手動ボタンだけにする。原則「置くだけ」は弱まるが循環は成立する）

削らないもの: 1杯ごとの「原因1つ・直す点1つ・予測1つ」、次の杯での当否判定、夜の振り返りと朝のテーマ、ピッチャーの残りの写真。迷ったら削るのは写真側で、音と検証ループは削らない（[decisions.md D10](decisions.md#d10-対象をミルクスチームに特化し工程をエア入れ撹拌の2つにする)）。

## デモの筋（3分）

1. 裂く音とゴボゴボの音を聞かせる（10秒）。「この違いが聞こえますか。家で一人だと、誰も教えてくれません」
2. 家で一人の練習者の困りごと: ラテアートの出来はスチームで決まるのに、スチームは見えず、失敗してもエア入れか撹拌か分からない。完成形を採点するアプリはあるが、原因は写真に写らず音にしか残らない。固定フレームで撮ってみて、練習者に手間をかけさせてはいけないと分かった話
3. 「開始」を押して置くだけ。スチームが終わると通知、ピッチャーの残りを写真1枚
4. 届く通知: 「撹拌が原因。次はピッチャーを縁側へ寄せる。裂く音の後のゴボゴボが消えれば成功」
5. 次の杯: ゴボゴボが消えた音と、泡の整った残りの写真。コーチが「当たり」と記録し、「あなたの正解」に1行増える
6. 複数の指摘を採点役（Outcomes）が差し戻し、1点に絞られる瞬間
7. 夜にコーチが振り返り、翌朝「昨日はエア入れが長い杯ほど滲んでいた。今日はこの1点」が届く
8. 限界を一言: 「渦の回転方向は聞こえません。だから結果で検証します」

## 受け入れ基準（11-08 の結果）

| 基準 | 結果 |

## 費用の方針

- Managed Agents はトークン料金に加え、セッション稼働1時間あたり $0.08 かかる。20杯程度ではクレジットを使い切らない
- 使い切ることを目的にせず品質に回す（毎杯の写真評価に上位モデルを使う、Outcomes の差し戻しを惜しまない）
