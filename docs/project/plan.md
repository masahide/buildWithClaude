# 計画と受け入れ基準

## 今日（11-03）確かめること

1. **Dreaming の利用申請を出す。** 承認までの時間が読めないため最優先
2. **診断セッションの待ち時間を測る。** コンソールでエージェントを1つ作り、テスト杯の写真でセッションを1回回す。Outcomes が「1点だけ」に絞るかも同時に確認する
   - 数十秒〜1分程度なら、1杯ごとの診断も Managed Agents で回す
   - 数分かかるなら、1杯ごとの診断は Messages API にメモリの中身を渡して呼び、Managed Agents は夜の振り返りと記録の蓄積に絞る
3. **カウンター置きで録音する。** ボイスメモで2〜3杯を通し録音する。窓はいつも通りの状態で、杯の自動区切りとエア入れ相の検出ができるか確認する

結果は [docs/log/](../log/) に書き、判断が出たら [decisions.md](decisions.md#未決) を更新する。

## スケジュール

記録ペース: 11-03〜11-07 に1日3杯以上、計15〜20杯。記録は 11-07 夕方までに終え、11-08 はデモ編集とリポジトリ整備に充てる。

| フェーズ | 期間 | 内容 |
| --- | --- | --- |
| 1. 基盤 | 11-03〜11-04 | 公開リポジトリ作成、iOS アプリのバックグラウンド録音、スチーム区間の自動検出、音響特徴量の計算、区間終了通知と写真撮影 |
| 2. コーチ | 11-04〜11-05 | サーバー、Managed Agents のエージェントとメモリストア、1杯ごとの診断セッションと Outcomes、Webhook とプッシュ通知、`rubric.md` のデータ化 |
| 3. 振り返りと検証 | 11-05〜11-07 | 夜のスケジュール実行（または Dreaming）、朝の通知、15〜20杯のラベル付きデータで診断結果と自己評価の対応を確認 |
| 4. 提出 | 11-08 | 3分デモ動画、プロジェクト概要、README 整備。締切 20:00 JST |

## デモの筋（3分）

1. 固定フレームで撮影してみて、練習者に手間をかけさせてはいけないと分かった話
2. 「開始」を押して置くだけ。スチームが終わると通知、写真1枚
3. 1杯ごとに、原因の工程と直す点1つが届く。複数の指摘を採点役が差し戻す仕組み
4. 夜にコーチが振り返り、翌朝「昨日はエア入れが長い杯ほど滲んでいた。今日はこの1点」が届く
5. 翌日の杯で実際に直った比較

## 受け入れ基準

- [ ] 練習開始を1回押すだけで、杯ごとのスチーム区間が自動で切り出される
- [ ] 音響特徴量が端末内で相対値として計算され、生の音声が端末外に送られない
- [ ] スチーム区間終了後の通知から完成写真を撮ると、原因の工程と「次の1杯で直す点1つ」がプッシュ通知で届く
- [ ] Outcomes のルーブリックにより、直す点が1つに絞られている
- [ ] 夜の振り返りで `/tendencies.md` と `/today.md` が更新され、翌朝通知が届く
- [ ] 検証データ15杯以上について、診断結果と自己評価の対応が記録されている
- [ ] 公開リポジトリに再現手順を含む README が揃い、API キーが含まれていない
- [ ] デモ動画が3分以内で、視聴可能な形式になっている

## 費用の方針

- Managed Agents はトークン料金に加え、セッション稼働1時間あたり $0.08 かかる。20杯程度ではクレジットを使い切らない
- 使い切ることを目的にせず品質に回す（毎杯の写真評価に上位モデルを使う、Outcomes の差し戻しを惜しまない）
