決めたこと・捨てたことを、理由とともに日付順に残す。新しい判断は末尾に追記する。

## D1. 固定フレーム撮影をやめ、置くだけの録音にする

- 日付: 2026-11-03
- 状態: 採用

固定フレーム（キング BE.SHOT）で俯瞰撮影を試した結果、スチーム工程の映像は取れたが、家庭の練習者には撮影準備が重すぎると分かった。

- 毎回スマホとピッチャーを同じ位置に固定する準備が大変
- 撮影中はスマホが邪魔で、スチームノズルを直接覗けない
- 撮影開始・停止の押し忘れ、ピンぼけの心配がある
- 雑音を避けるために窓を閉めるなど、環境の準備が増える
- ラテを作る手間に撮影の手間が上乗せされ、初心者は混乱する

ここから [overview.md](overview.md#設計原則) の設計原則を決めた。

この経緯は本人が自分で確かめた事実であり、デモの語りの芯にする。説明に他社製品の名前を借りない。

## D4. 工程の区分を「エア入れ／撹拌／注ぎ」にする

- 日付: 2026-11-03
- 状態: D10 で「エア入れ／撹拌」の2工程に改訂

当初は原因を「スチーム／ミルク／注ぎ」に割り当てていた。これを「エア入れ／撹拌／注ぎ」に変える。

- 音の2相（エア入れ相・撹拌相）と工程が1対1で対応し、音から工程を直接指せる
- ラテアートの出来を最も左右するのは撹拌（ノズルの深さ、渦、泡の縦横の折り込み）であり、独立した工程として扱わないと「スチームが原因」で診断が止まってしまう
- ミルクの銘柄・量・温度は杯ごとの動作ではなく条件なので、工程から外して `/profile.md` に持たせる

## D5. 完成写真にピッチャーの残りを入れる

- 日付: 2026-11-03
- 状態: 採用（残りの状態が写真で読めるかは今日の杯で確認する）

音は撹拌の結果を部分的にしか拾えない。指導者がよく行う「ピッチャーに残ったミルクを見る」を、既存の完成写真1枚に乗せる。注ぎ終わったらカップの隣にピッチャーを置いて1枚撮る。

- 残りが固く乾いた泡なら空気過多、大きな泡が残っていれば渦ができていない、艶があって塗料のように流れれば良好
- 泡が上に乗って分離していれば、縦の折り込み不足
- 撹拌の良否を注ぎから切り離して判定できる
- 「1杯に写真1枚」の原則は崩れない。スチーム直後には撮らない（D3）

## D6. 音響特徴量に包絡を加える

- 日付: 2026-11-03
- 状態: 採用

スカラー値だけでは、エア入れ相から撹拌相への形がコーチに伝わらない。スチーム区間の帯域エネルギー（3帯域）を0.1秒ごとに記録した相対値の数列（包絡）を加えて送る。

- コーチが相の形を直接読める。アプリでも小さなグラフとして見せられる
- ノズルが深すぎたときのこもった轟音は、撹拌相の低域比率としてスカラー値にも加える
- 数列からは会話を復元できないため、「生の音声は端末から出さない」は維持される

## D7. 診断を仮説と予測の形にし、次の杯で検証する

- 日付: 2026-11-03
- 状態: 採用

スチームの正解は熟練者の耳と手の中にあり、コーチも本人の機材とミルクでの正解を最初から持っているわけではない。そこで診断を仮説の形にする。

1. 症状（音と写真）から原因の工程を1つ推定する
2. 直す点を1つ返し、「次の杯で音や残りがこう変わるはず」という予測を1つ添える
3. 次の杯でその予測の当否を判定する
4. 当たった直し方を `/rules.md` に溜め、「あなたの正解」として本人に見せる

渦の回転方向のように観測できない動作でも、症状→推定→指示→次の杯で検証、の循環で直せる。「AIはどう正解を知るのか」という問いへの答えであり、単発の画像解析ツールとの違いでもある。

## D8. 指示は耳・手・時間で実行できる言葉に限る

- 日付: 2026-11-03
- 状態: 採用

スチーム中に cm や温度は測れない。直す点は「裂く音を今より1秒短く」「ピッチャーを縁側へ寄せる」「沈めるのを今より早く」のように、耳で聞き、手で動かし、時間で数えられる形に限る。Outcomes のルーブリックで強制する。

副次効果として、ユーザーは自分の耳で確かめる習慣がつく。コーチへの依存ではなく、耳を育てる方向になる。

## D9. 音で分からないものを明文化する

- 日付: 2026-11-03
- 状態: 採用

音と写真で判定できるのは工程の結果（症状）であり、動作そのものではない。

| 分からないもの | 代わりに見るもの |
| --- | --- |
| 渦の回転方向 | ピッチャーの残りの泡の大きさ、撹拌相のゴボゴボの回数 |
| 縦横の撹拌のバランス | 残りの分離、注ぎの最初の水っぽさと最後の泡の塊 |
| ノズルの正確な位置と深さ | エア入れ相の長さ、撹拌相の低域比率 |

この限界は README とデモで明言する。製品は動作を観測せず、D7 の循環で直す。過大な主張を避け、限界を知った上で設計していることを示す。

## D10. 対象をミルクスチームに特化し、工程を「エア入れ／撹拌」の2つにする

- 日付: 2026-11-03
- 状態: 採用

既存アプリの調査（[log/2026-11-03.md](../log/2026-11-03.md#既存アプリの調査)）で、完成写真を採点して「次の1杯で直す点を1つ」返す型は既に市場にあると分かった。一方、スチームの音で工程を診断するものは見つからなかった。この企画の芯は音にあるので、製品の主語をラテアートからミルクスチームに移す。

- 工程は「エア入れ／撹拌」の2つにする。音の2相と工程が完全に1対1になり、ルーブリックと Outcomes の判定が単純になる。「注ぎ」は音と無関係で、完成形からの推定も弱かった（D2 は対象外になる）
- 検証の軸はピッチャーの残りの写真にする（D5 は維持）。カップの完成写真は任意に下げ、採点しない
- 困りごとの導入はラテアートで語る。スチームの失敗は見えず、カップに注いで初めて現れる、という見える化の役。製品の対象ではない
- 当事者性は「家で一人で練習する人」のまま。カフェの新人教育など対象の広がりは README の「次にやること」に書く
- 残り5日のスコープが縮む。削るのは写真側の機能で、音と検証ループは削らない

D1・D5〜D9 はそのまま有効。D4 の3工程は本判断で2工程に改める。

## D11. 最初の一周は手動区切りで回し、自動区切りと包絡を後回しにする

- 日付: 2026-11-03
- 状態: 採用

11-05 の夜までに「録る → 送る → 診断がアプリに表示される」の一周を回すことを優先する。[plan.md](plan.md#時間が足りないときに削る順) で削る候補に挙げていた次の2つを、最初の版から外す。

- 杯の自動区切り: 「この杯を区切って撮る」ボタン1つで、区切りと写真撮影をまとめて行う。スチームの鳴り終わりの判定だけは入れ、区間終了のローカル通知に使う（区切りには使わない）
- 包絡の送信: 端末内では0.1秒ごとの3帯域エネルギーを計算するが、送るのはスカラーの特徴量だけにする
- 診断結果はプッシュ通知ではなく、アプリがサーバーに取りに行く（3秒ごと）。届いたらローカル通知を出す

一周が回った後、検証データを見て自動区切りと包絡を戻すか決める。開発は Mac に寄せ、Windows では編集しない（2台で編集すると衝突の処理に時間を取られるため）。

## D12. 無料の Apple ID で開発し、リモートのプッシュ通知を使わない

- 日付: 2026-11-03
- 状態: 採用

有償の Apple Developer Program に登録していない。無料の Apple ID（Personal Team）でも実機に入れられ、バックグラウンド録音・マイク・カメラ・ローカル通知は使える。使えないのはリモートのプッシュ通知（APNs）と TestFlight で、アプリは7日ごとに入れ直す必要がある。

- 1杯ごとの診断は、アプリがサーバーに取りに行き、届いたらローカル通知を出す（D11 の形をそのまま本採用にする）
- 朝の通知は、決まった時刻に端末でローカル通知を出し、開いたときに今日のテーマを取りに行く
- 練習仲間には TestFlight で配れないので、本人の iPhone で録るか、相手の Mac から入れてもらう
- 開発中のサーバーは同じ Wi-Fi の Mac で動かし、アプリからは `http://<Mac の名前>.local:8000` に送る。http はローカルネットワークだけ許可する
- 署名チームとバンドル ID は `ios/Config/Local.xcconfig`（git 管理外）に置き、公開リポジトリに入れない

配布が必要になったら登録を検討する。審査はデモ動画とリポジトリで行われるので、提出には登録が要らない。

## D13. 1杯ごとの診断を Managed Agents＋Outcomes で回す

- 日付: 2026-11-03
- 状態: 採用

同じ写真と仮の特徴量で、診断の待ち時間を測った（[log/2026-11-03.md](../log/2026-11-03.md#診断の待ち時間)）。Managed Agents＋Outcomes は送ってから診断まで約68秒、Messages API は約15秒だった。

- 決めておいた基準（「数十秒〜1分なら Managed Agents」）の範囲に収まる。杯の間には豆を挽いて抽出する数分があり、約1分の待ちは練習の流れを止めない
- Outcomes の採点役が、1点に絞れているかを毎杯確かめる。デモの「差し戻されて1点に絞られる瞬間」もこの方式でしか見せられない
- 杯ごとのセッションの記録が残るので、夜の振り返りと Dreaming（承認されたら）の入力にそのまま使える
- 計測は1回だけなので、実録音の杯でも時間を記録する（サーバーが `elapsed_sec` を残す）。2分を超えるようなら、サーバーの `COACH_BACKEND=messages` に戻す。コードは両方ある

## D14. 包絡を閾値の調整のために先に送る

- 日付: 2026-11-04
- 状態: 採用（コーチへの渡し方は D16）

D11 で送信をスカラーの特徴量だけにした。しかし最初の実録音で、40〜60 秒のスチームが 14〜19 秒しか検出されなかった。さらに、始めと終わりの「キュルルル」や前後の空だしが、高域を手がかりにしたエア入れの判定と区別できていない疑いが出た（[log/2026-11-04.md](../log/2026-11-04.md)）。合成音だけで閾値を決めるのは限界なので、実際の音の形を見て判定を作り直す。

- 区切りまでの帯域エネルギーの包絡（0.1 秒ごとの [低, 中, 高]、背景音比、有効数字3桁）を、杯ごとにサーバーへ送って保存する。音声ではなく会話も復元できないので、生の音声を端末外に出さない原則は保たれる（D6）
- コーチにはまだ渡さない。相の判定が直ったら、D6 のとおりコーチに読ませるかを決める

## D15. スチームの区間と相の判定を、実際の録音に合わせて作り直す

- 日付: 2026-11-05
- 状態: 採用（録音1本で合わせた暫定。2本目で確かめる）

本人の練習をボイスメモで録り、解析した（[log/2026-11-05.md](../log/2026-11-05.md)）。その結果、合成音で決めた判定は実際の音に合わないと分かった。渦の撹拌相は背景より数 dB しかなく、区間が途中で切れていた。いちばん高い音は泡入れではなく、蒸気を出した直後の「キュルルル」だった。

- スチーム区間は、1 秒平均の音量にヒステリシスをかけて決める。大きい音が2秒続いたら始まりとし、約1秒の空だしを除く
- 始めの「キュルルル」を別に測り、エア入れの割合に含めない
- 泡入れと渦の境は、音の高さではなく「音量の揺れ」が減るところ（変化点）で決める
- 撹拌の値は、止める間際の「キュルキュル」を除いて測る
- 開発中の判定合わせに限り、本人の Mac の中でボイスメモを解析する。音声ファイルは git 管理外に置き、製品の経路（端末外に送るのは特徴量・包絡・写真だけ）は変えない

## D16. 音を絵にして Claude に見せ、判定は端末の数値のままにする

- 日付: 2026-11-06
- 状態: 採用（設計のみ。[sound-picture.md](sound-picture.md)）

OpenAI の Codex が、音をスペクトログラム（短時間フーリエ変換の画像）にして自分で見て確かめている例を知った（11-05、AIMIX Meetup での紹介の投稿）。同じように音を絵にして見せる方法を検討した。Claude も音を直接聞けないが、絵なら読める。一方、アプリの判定（スチーム区間と相の境）を絵に置き換えると、再現性・待ち時間・端末から出る情報の点で損をする。11-04 の失敗の原因も、数値で判定したことではなく、実際の音を見ずに閾値を決めたことにあった。

- 絵は、Claude が音を読む場面に使う。判定を作る Claude Code には、ボイスメモから描いた答え合わせ図（音の形・アプリの判定の境・本人の耳の境を重ねたもの）を見せる。コーチには、包絡から描いたスチーム区間の絵を見せる
- 区間と相の境を決めるのは、これまでどおり端末内の数値の判定。判定の計算はアプリの Swift の1か所だけに置き、開発用のコマンドもそれをコンパイルして使う。アプリは境の位置（`marks`）も送り、絵の縦線に使う
- コーチには、包絡を数列ではなく絵で渡す。D14 で残していた「コーチに読ませるか」への答え。端末から出る情報は増えない。サーバーがスチーム区間だけを切り出して描く
- 前の杯の絵も並べて、予測の当否を確かめる材料にする。絵は判定の方法に依らないので、判定を作り直した前後の杯も比べられる
- コーチが判定の線と絵の食い違いに気づいたら `judgment_doubt` に書かせ、判定の作り直しに使う
- コーチに渡す前に、絵が読めるかを1回確かめる。組み込んだ後も、絵ありと絵なしで数杯を比べ、読み違いがあれば外す（`COACH_SOUND_PICTURE`）
- 期限が近いので、コーチへの組み込みは夜の振り返りより後にし、間に合わなければ削る。答え合わせ図と杯ごとの絵（README とデモに使う）は残す

## D17. 泡入れを1回と決めつけず、追加の泡入れを別に数える

- 日付: 2026-11-06
- 状態: 採用

D15 では、泡入れ→渦の境を1か所だけ求めていた。AI エージェントに同じ録音を6回解析させると、この境が 23 / 30 / 32 秒に割れた（[log/2026-11-06.md](../log/2026-11-06.md)）。本人に聞くと、泡入れは 16〜23 秒で、一度静かにしたあと、泡が足りないと思って 27〜32 秒に追加で泡入れしていた。境があいまいだったのではなく、泡入れが2回あった。

- 音量の揺れが大きい区間をすべて泡入れとして拾う。最初の泡入れの長さ、追加の泡入れの回数と長さを別の特徴量にする（`first_air_sec`、`re_air_count`、`re_air_sec`）。2.5 秒未満の揺れは、渦の中のゴボゴボとして泡入れに数えない
- 渦への境は、最後の泡入れの終わりにする
- この録音での判定（耳との差）: 最初の泡入れ 16.2〜23.4 秒（+0.2 / +0.4）、追加 26.6〜32.4 秒（−0.4 / +0.4）
- 追加の泡入れは、この杯の「泡が少し多かった」につながる候補で、コーチが直す点として指せる。デモで狙う1点の候補にする
- 撹拌中に「チリチリ」と少し空気が入ってしまうこともある（本人）。今の特徴量では拾っていない。録音が増えたら、高域の短い揺れとして別に数えるか検討する

## D18. AI もユーザーも初心者から始まり、一緒に育つコーチにする

- 日付: 2026-11-07
- 状態: 採用

スチームのやり方は人によって違い、マシンによって音の質も長さ（家庭用でも 15〜60 秒）も違う（[log/2026-11-07.md](../log/2026-11-07.md)）。「誰のどんなスチームでも、音だけで良し悪しを採点する」汎用の判定器は作れない。作るのは、その人の杯どうしを比べ、一緒に正解を見つけていくコーチ（D7）である。本人と話して、これを製品の芯として言い切ることにした。

今週の開発で実際に起きたことが、その形になっている。最初の判定は作り物の音で決めた「初心者の耳」で、40〜60 秒のスチームを 14 秒で切っていた。本人が耳で「ここが泡入れ、27〜32 秒は追加の泡入れ、チリチリはここ」と教え、AI は図と解析で「チリチリは 4〜8 kHz の山」「泡入れは音量の揺れで見分けられる」と返した。その往復で、判定は耳と ±0.4 秒で一致するまで育った。本人も、自分の追加の泡入れが音に出ていることを知った。

- **ユーザーが育つ**: 毎杯、直す点を1つ試し、自分の耳で確かめる（D8）。翌朝、今日のテーマを受け取る
- **コーチが育つ**: 毎杯、予測を立て、次の杯で当否を確かめる（D7）。毎晩の振り返りで、当たった直し方を「あなたの正解」（`/rules.md`）に、外れた読みや本人に教わったことを「この人の音の読み方」（`/reading.md`）に書き足す。1杯ごとの診断は、それを読んでから行う
- 記憶は Managed Agents のメモリストアに置く（`server/memory.py`）。1杯ごとの診断は読むだけ、夜の振り返り（`server/review.py`）が書く
- iPhone の判定そのもの（閾値）は自動で書き換えない。録音と本人の耳で答え合わせして、人が直す（D15〜D17 の進め方）。→ D20 で、コーチが提案し本人が承認する形に改めた
- アプリに「コーチと一緒に育つ」として、今日のテーマ・あなたの正解・コーチが学んだことを出す
- README とデモは「AI もユーザーも初心者から始まり、一緒に育つ」で語る。汎用の採点器ではないこと、確かめたのは本人1人・1台であることを明言する

## D19. コーチに加工前の音の形も渡す（音の絵と包絡）

- 日付: 2026-11-07
- 状態: 採用

本人から「アプリで判定した加工データだけより、情報は多いほうがコーチが育つ要素になるのでは」と提案があった。そのとおりと判断した。アプリの特徴量は、今わかっている範囲の切り取り方で固定されている。今週の発見（泡入れが2回あった、チリチリは 4〜8 kHz の山）は、数値ではなく元の形を見て見つかった。コーチにも元の形を渡せば、数値にない出来事に自分で気づき、「コーチが学んだこと」に書ける。

- 1杯ごとの診断: 数値・写真・記憶に加えて、その杯と前の杯の**音の絵**を渡す（`server/sound_picture.py`。帯域ごとの音量、音量の揺れ、アプリの判定の境）。判定と診断の根拠は数値を正とし、絵は補助。絵を根拠にするときは何秒あたりの何を見たかを書かせ、判定の線と形の食い違いは `judgment_doubt` に書かせる。`COACH_SOUND_PICTURE=0` で外せる
- 夜の振り返り: その日の杯の**包絡のデータそのもの**と絵を作業用の環境に置き、コーチが自分で Python で解析して杯どうしの形を比べられるようにする。時間の制約がないので、毎杯ではなくここで深く読む（エージェントの解析は1回 2.5〜4 分かかった。log/2026-11-06）
- アプリが送る包絡に 4〜8 kHz の帯域を足す（チリチリが出る）。判定（泡入れなど）は変えない。アプリは判定の境の位置（`marks`）も送る
- 端末から出るのは、これまでどおり包絡と写真だけ。生の音声は送らない
- 画像だけでは判定がアプリに劣る（log/2026-11-07）ので、絵を判定の代わりにはしない（D16 は維持）

## D20. 判定の閾値は、コーチが提案し、本人が承認して変える

- 日付: 2026-11-07
- 状態: 採用（D18 の「閾値は自動で書き換えない」を、この形に改める）

本人から「検出の閾値なども、AI エージェントの判断で修正できるようにしたほうがよいのでは」と提案があった。マシンによってスチームの長さも音も違うので、閾値をその人・そのマシンに合わせていく仕組みは要る。一方、AI が黙って書き換えると、次の2つが起きる。

- 杯どうしの比較が崩れる。予測の検証（D7）は同じ物差しで測るのが前提で、物差しが黙って変わると、変化が直し方の効果なのか分からなくなる
- 答え合わせなしの調整になる。11-04 と 11-07 に、正解のないところで数値に合わせて判定が実際からずれた

そこで、変更は提案と承認の形にする。

- 閾値はサーバーで版つきで持つ（`server/params.py`、`GET /params`）。アプリは練習の開始時に今の版を取りに行って判定に使い、杯ごとに版を記録する（`params_version`）
- 夜の振り返りで、コーチが包絡の解析と本人に教わったことを根拠に、変えたほうがよいと言えるときだけ提案する。名前と範囲はサーバーで検査し、範囲の外は収める
- 本人がアプリの「コーチから判定の調整の提案」で、変更・理由・根拠を見て、適用するか見送るかを決める。適用すると版が上がる
- 提案・適用・見送りの履歴を、コーチの記憶（`/params.md`）に残す。コーチは版が違う杯どうしの数値を直接比べない
- 音の絵の描き方（判定と比較に影響しない）は、コーチの判断で変えてよい範囲として残す（今は未実装）
- 確かめた範囲: 提案と見送りの流れ、範囲外の値と知らない名前の扱い、アプリの既定値と v1 が一致すること（テスト9本）。コーチが実際に提案を出すかは、今夜の振り返りで確かめる
