# 音の絵

Claude は音を直接聞けない（[timeline.md](timeline.md) の 11-05）。きっかけは、OpenAI の Codex が音をスペクトログラムの画像にして確かめている例を見たこと（11-05、AIMIX Meetup での紹介の投稿）。同じように、音を絵（横軸が時間、縦軸が音量や周波数の図）にして見せる。見せる相手は、判定を作る Claude Code と、診断するコーチの2者。アプリが区間や相の境を決める判定そのものは、絵に置き換えない。判断の理由は [decisions.md D16](decisions.md#d16-音を絵にして-claude-に見せ判定は端末の数値のままにする)。

最終更新: 2026-11-06（設計のみ。未実装）

## 結論

| 場面 | 誰が見るか | 何に使うか | いつ |
| --- | --- | --- | --- |
| A. 判定の答え合わせ図 | Claude Code と本人 | ボイスメモの音の形、アプリの判定の境、本人が耳で聞いた境を1枚に重ね、ずれを見つける | 11-06。[status.md](status.md) の次にやること1をこの図で行う |
| B. 杯ごとの音の絵 | 本人と Claude Code | サーバーが、送られてきた包絡からスチーム区間の絵を描いて保存する。実際の杯の判定を目で確かめる。デモと README にも使う | 11-06。A の後 |
| C. コーチに絵を渡す | コーチ（Managed Agents） | 今回と前の杯の絵を、特徴量・写真と一緒に渡す | 11-07 の朝まで。夜の振り返りより後。間に合わなければ削る |
| D. アプリで見せる | 本人 | 診断と一緒に自分の音の絵を見る | 後回し |

区間の始まりと終わり、泡入れから渦への境を決める「検知」は、これまでどおり端末内の数値で行う。

## 検知を絵に置き換えない理由

- 端末の判定は、区切った瞬間に通信なしで値が出て、同じ音なら毎回同じ値になる。予測の検証（D7）は杯どうしの数値の比較なので、この再現性を手放せない
- 絵で検知するには、絵を見る役が要る。Claude に見せるなら、サーバーへ送る情報が増え、1〜2分の待ちにさらに足される。端末で画像の分類モデルを使うなら、境のラベルが付いた録音が数十本単位で要るが、今は2本しかない
- 11-04 の失敗の原因は、数値で判定したことではない。実際の音を見ずに、合成音で閾値を決めたことにあった（[log/2026-11-04.md](../log/2026-11-04.md)、[D15](decisions.md#d15-スチームの区間と相の判定を実際の録音に合わせて作り直す)）。直すべきは「判定を作る人が実際の音を見られること」で、そこに絵が効く

## 絵が効く理由

- 0.1 秒刻みの包絡は、スチーム区間だけでも 500〜700 個の [低, 中, 高] になる。数列のまま読ませると、トークンが多いうえに「どこで揺れが収まったか」のような形を読み違えやすい。絵なら1枚で形が伝わる
- 本人の耳と Claude の目を、同じ時間軸の上で突き合わせられる。本人は「ここで渦に入った」と秒で言えばよい
- 包絡から描いた絵は、判定の方法を変えても描き方が変わらない。判定を作り直しても、絵どうしなら前後の杯を比べられる（特徴量の数値は D15 の前後で比べられなかった）

## 共通: 判定の境の位置（marks）

A〜C のすべてで、アプリの判定の境に縦線を引く。そのために、`FeatureExtractor.extract` が特徴量と一緒に境の位置を返すようにする。位置は、包絡（区切りまでのフレーム列）の先頭からの秒。

```json
"marks": {"steam_start": 12.3, "squeal_end": 16.9, "transition": 33.1, "stir_end": 65.4, "steam_end": 68.4}
```

| 名前 | 意味 |
| --- | --- |
| `steam_start` / `steam_end` | スチーム区間の始まりと終わり |
| `squeal_end` | 始めの「キュルルル」の終わり |
| `transition` | 泡入れから渦（撹拌）への境 |
| `stir_end` | 撹拌の値を測る範囲の終わり（止める間際のキュルキュルを除いた位置） |

- **判定に関わる計算は、アプリの Swift の1か所だけに置く。** Python に判定を書き写すと、残り2日のうちに食い違う。絵にしか使わない計算（細かいスペクトログラム、揺れの列の描画）は Python でよい
- アプリは `marks` を杯の記録に持ち、特徴量と一緒にサーバーへ送る。次の iPhone への入れ直しに乗せる
- `marks` のない杯は、音量が背景より +10 dB を超える最初と最後の位置で大まかに切り出し、縦線を引かない

## A. 判定の答え合わせ図

開発用で、本人の Mac の中だけで作る。[status.md](status.md) の次にやること1（2本目のボイスメモで判定を確かめる）を、この図で行う。

### 作り

| 部品 | 役割 |
| --- | --- |
| `scripts/voice_memo/judge.swift` | アプリの [FeatureExtractor.swift](../../ios/LatteCoach/Audio/FeatureExtractor.swift) と一緒に `swiftc` でコンパイルする macOS のコマンド。ボイスメモ（m4a でも WAV でも）を AVAudioFile で読み、3帯域の包絡・背景音・`marks`・特徴量を JSON で出す |
| `scripts/voice_memo/picture.py` | 上の JSON と、本人の耳のラベル（任意）から図を描く。細かいスペクトログラムは、音声から Python（numpy）で計算する |
| `server/sound_picture.py` | 図を描く部分。B・C と共通にする |

背景音は、アプリと同じく開始直後の数秒（空だしの前）の中央値にする。

### 図の中身（上から。横軸は共通の秒）

1. 細かいスペクトログラム: 50 Hz〜8 kHz を対数で 64 本、0.1 秒刻み、背景音比の dB。始めのキュルルル（3〜4 kHz）と止める間際のキュルキュル（1.3 kHz あたり）の高さを見分けられる
2. 帯域ごとの音量: アプリと同じ3帯域（低・中・高）の背景音比 dB を3本の線で
3. 音量の揺れ: アプリが泡入れと渦の境を決めるのに使う列（±0.5 秒の標準偏差を 1 秒平均したもの）
4. 縦線: アプリの判定の境（実線）と、本人の耳の境（破線）

### 手順

1. 本人がボイスメモを聞き、境の時刻を `notes/private/recordings/<名前>.labels.json` に書く（キュルルルの終わり、渦に入った、キュルキュルの始まり、止めた）。±1 秒くらいでよい。書きにくければ、先に Claude Code が図から境の候補を読み、本人が耳で確かめる
2. 図を描き、Claude Code が見る。判定の境と耳の境の差が ±3 秒以内か確かめる
3. ずれていたら、図のどの段で何が起きているか（揺れが収まらない、破裂で揺れが戻る、など）を手がかりに判定を直し、描き直す。直したら合成音のテストも通す
4. 結果を `docs/log/` に表で残す（録音ごとに、判定の境・耳の境・差）

### 扱い

- 図と JSON は `notes/private/pictures/`（git 管理外）に置き、コミットしない
- Claude Code が図を見ると、その画像は Anthropic の API に送られる。D15 の例外（開発中の判定合わせに限り、本人の録音を本人の Mac で解析する）の範囲として扱い、次の2つで絞る
  - 描くのはスチーム区間と、その前後の空だしまで（前後10秒ほど）。会話が入りやすい時間を描かない
  - 時間方向は 0.1 秒刻みより細かくしない。数ミリ秒刻みのスペクトログラムは音声にかなり戻せるので作らない。Codex の例は楽曲の音の高さを読むために 2.9 ms 刻みだったが、ここで見たいのは秒単位の相の移り変わりなので、そこまでの細かさは要らない
- 音声ファイルそのものは、これまでどおりどこにも送らない

## B. 杯ごとの音の絵

サーバーが杯を受け取ったら、包絡からスチーム区間の絵を描いて保存する。端末から出る情報は増えない（D14 で送って保存している包絡から描く）。

### 絵の仕様

| 項目 | 決め |
| --- | --- |
| 範囲 | `steam_start` の5秒前から `steam_end` の5秒後まで。区間の外は描かない |
| 横軸 | 蒸気を出してからの秒。全杯で同じ尺（−5〜75 秒。長い杯は延ばす）。5 秒ごとに目盛り線と数字 |
| 上段 | 音量（背景音比 dB）。0.1 秒の値を薄く、1 秒平均を濃く。縦軸は全杯で固定 |
| 中段 | 帯域ごとの音量（低・中・高の3本）。縦軸は全杯で固定 |
| 下段 | 音量の揺れ（A の3段目と同じ計算）。縦軸は全杯で固定 |
| 縦線 | `marks` の位置に実線と短い名前（始まり、キュルルル終わり、渦へ、測定終わり、止めた） |
| 大きさ | 1500×900 px 程度の PNG。文字は大きめにする。日本語はヒラギノを指定し、文字化けしないか最初に確かめる |
| 色 | 3帯域は色覚の差で見分けにくくならない3色にし、線の種類も変える |
| 保存先 | `server/data/cups/<id>/sound.png`（git 管理外） |

縦軸を全杯で固定するのは、杯どうしを並べたときに高さで比べられるようにするため。

### 使い方

- 実際の杯の判定を、本人と Claude Code が目で確かめる。ボイスメモのない杯でも、境が明らかにずれていれば分かる
- README とデモに使う。「見えないスチームの音が、形として見える」を示す。公開するのはこの B の絵だけにする（端末から出ている情報と同じ粒度）。A の細かい図は載せない

## C. コーチに絵を渡す

### 入れる前の確認（30分ほど）

絵が読めるかだけ、先に確かめる。A の JSON の3帯域から B と同じ形の絵を描き、Messages API に1回見せる。「揺れが収まる秒」「中域のトゲの数とおよその位置」「低域が上がる区間」を答えさせ、アプリの判定と比べる。境が ±3 秒、トゲの数が ±2 に収まれば組み込む。外れるなら、段の構成や縦軸を直すか、C をやめる。

### 渡し方

- 今回の杯の絵と、前の杯の絵（あれば）を、写真と並べて渡す。どれが何かを本文に書く（「1枚目: 前の杯の音の絵、2枚目: 今回の音の絵、3枚目: ピッチャーの残り」）
- `marks` は数値では渡さない。絵の縦線として渡す
- プロンプトに絵の読み方を足す
  - 段と縦線の意味
  - 絵は、数値に出ない形を読むのに使う。例: 揺れがいつ、どのくらい急に収まったか。ゴボゴボ（中域のトゲ）が区間のどこに集まるか。低域が途中から上がるか（ノズルが沈んだ疑い）
  - 絵を根拠にするときは、何秒あたりの何を見たかを書く
  - 前の杯の予測の当否は、まず数値で、次に2枚の絵の違いで確かめる
  - 縦線が絵と食い違って見えたら（例: 揺れが 40 秒まで続くのに「渦へ」が 30 秒にある）、診断は数値のまま行い、食い違いを `judgment_doubt` に書く
- 診断の JSON に `judgment_doubt`（任意、なければ null）を足す。アプリには表示しない。サーバーの記録に残し、判定の作り直しの手がかりにする
- ルーブリックに1行足す: 「音の絵を根拠にするときは、何秒あたりの何を見たかを書いている」
- 環境変数 `COACH_SOUND_PICTURE`（既定 1）で外せるようにする。外すと、今までどおり数値と写真だけで診断する

Anthropic に渡る情報には、スチーム区間の包絡を描いた絵が加わる。これは D6 で予定していた「コーチが相の形を直接読む」の範囲に収まる。区間の外を切り落とすので、包絡を丸ごと渡すより少ない。

### 残すか外すかの基準

3〜5杯で、同じ杯を絵ありと絵なしの両方で診断し、`docs/log/` に並べる。

- 絵ありの根拠に、絵の読み違い（絵にない形を書く）がないか。明らかな読み違いが1杯でもあれば、既定を外す
- `judgment_doubt` が出た杯で、B の絵を本人と見て、本当に判定がずれていたか
- 前の杯の予測の当否が、絵ありで具体的になったか（何秒あたりで何が変わったか）
- 待ち時間（`elapsed_sec`）が大きく延びていないか

## D. アプリで見せる

診断の画面に、その杯の音の絵を出す（サーバーから `GET /cups/{id}/sound.png` で取る）。耳で聞いた音と絵の形を結びつけ、耳を育てる（D8）。11-08 までは作らず、README の「次にやること」に書く。

## 採らない案

| 案 | 理由 |
| --- | --- |
| 絵を Claude に見せて区間や相の境を決める（検知を置き換える） | 送る情報が増え、待ちが延び、同じ音でも結果が揺れる。予測の検証（D7）の数値比較が崩れる |
| スペクトログラムを入力にした分類モデルを学習する | 境のラベル付きの録音が2本しかない。期間後に録音が溜まったら検討する |
| 端末で細かいスペクトログラム（数十本の帯域）を計算して送る | 端末から出る情報が増える。今の現象（キュルルル、揺れ、低域）は3帯域で見える。キュルルルとキュルキュルの高さの違いを見たくなったら再検討する |
| コーチ自身に、包絡の数列から絵を描かせる | 毎杯描き方が変わり、杯どうしで比べられない。待ちも延びる |
| 包絡の数列をそのままコーチに渡す | 数百個の数列で、形を読み違えやすい |
